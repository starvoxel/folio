Jeremy is leaning towards Electron because he wants a web version later, but is unhappy with Electron's size and memory. The result may confirm Electron, and that is a fine outcome. Honest measurement matters more than a polished app.

## What to build

The same slice as `SLICE-SPEC.md`, with the **same renderer** as the Electron slice (React, TypeScript strict, Fluent UI React v9, TanStack Virtual, ECharts) inside a **Tauri 2** shell. Put code under `tauri/`.

- Use the current stable Tauri 2.x line (for example 2.12.x), pinned exactly, and the Rust stable toolchain. Do not use the Tauri 3 alpha for the main slice. CEF (a bundled Chromium) is reported to exist only in the Tauri 3 alpha, to be experimental, to add hundreds of MB and to be unavailable with the Windows Chromium sandbox: confirm or refute that yourself from the sources and say what you read. If time allows after the main slice is finished, do one short timeboxed trial of the CEF runtime on one OS and report size, memory and whether it starts. This is optional and comes last.
- Keep the renderer shell-agnostic. Define a small `HostApi` TypeScript interface (load fixture data, open dialog, state hook for tests, quit) with a Tauri adapter. Copy the renderer from the Electron branch and change as little as possible. **Record exactly how many lines of renderer code and how many lines of host code changed**, because shell portability is a decision input.
- Fixtures: load `fixtures/*.json` from a path given by an environment variable or command-line argument, through a Rust command or the fs plugin with the narrowest capability and scope you can. Use the least permissions that work (deny by default, a minimal capability file) and record them.
- The test and agent-drivability hook stays: structured page state and navigation, available only when started with an automation flag or environment variable, off by default, and refused in any other case. Describe how you gate it in Rust.
- Privacy hardening, applied from the start, not after the capture: a strict CSP through the Tauri config, no updater plugin, no telemetry or other plugins that make network calls, no remote assets, no external URL handling, and `withGlobalTauri` and other broad conveniences off unless needed. For each web view, find out what it can do on its own: see G1 below.
- Rust burden. Besides the slice, spend about one hour on the minimal Rust that the real app would need for safe file handling, in a separate small module: an atomic save (write a temp file, fsync, rename over the target, fsync the directory where the OS allows), and an in-use lock file with stale-lock detection. Report the lines of Rust and what you could not make work from TypeScript with the official fs plugin (it has no fsync and no file lock). Also wire up CSV drag-and-drop onto the window using Tauri's native drop event, and report the known conflict between native file drops and browser drag-and-drop on Windows and macOS. Keep all this out of the measured slice if it distorts the numbers.

## Gates and measurements

All six gates in `SLICE-SPEC.md` apply, measured as in the Electron slice so the numbers compare. The Tauri-specific points follow.

- **Memory (G2, F1). This is where a naive measurement flatters Tauri, so be careful.** The page runs in OS-owned web view processes that may not be children of the app process. On Linux the WebKit web and network processes are children of the app. On Windows the WebView2 processes (`msedgewebview2.exe`) normally are children, but check. On macOS the WebKit content, GPU and network processes are separate system-launched processes that are not descendants of the app. **If you only sum the app's own process tree you will undercount and Tauri will look falsely light.** For each OS, find every process that belongs to the app's web view (for example by the WebView2 user data directory in its command line, by `ps` and `footprint` for the WebKit processes that the app started, or by parent and XPC relationships), include them all, and write down exactly how you found them and how you know you got them all. Report the app-only figure and the all-processes figure separately. Use the F1 metrics and points from `FOLLOWUP-SPEC.md` (Linux PSS, Windows private working set, macOS footprint; P0 to P5). Compare with the Electron numbers.
- **Footprint (G5).** Measure the installer or package sizes Tauri's bundler really produces: Windows (note which WebView2 install mode: download bootstrapper, embedded bootstrapper, offline installer or fixed version, and its size), macOS app and dmg, Linux deb, rpm if easy, and AppImage. The runtime dependency on the OS web view is a real cost to describe, for example WebView2 missing on old Windows, or `libwebkit2gtk-4.1` for the deb. Cold start as in the Electron slice.
- **Privacy (G1). The headline risk for this stack.**
  - Linux: the same namespace, `strace` and `tcpdump` capture as the Electron slice, with launch, every page and five minutes idle, using the same analyzer (it also reports DNS lookups for external names). Report any `connect()` or lookup to a non-loopback address. Check WebKitGTK's settings that matter: hyperlink auditing (`<a ping>`) and DNS prefetching, and whether spellcheck or other services make requests. Find in the `wry` source whether anything is set.
  - Windows: Microsoft documents that the WebView2 Evergreen runtime collects required diagnostic data regardless of the Windows diagnostic setting, and that the app can only control SmartScreen and custom crash reporting. Capture what you can on the Windows runner for the whole web view process tree (for example sampling per-process sockets and `pktmon`), validating the sampler the way the Avalonia session did. Try the available controls (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, the data directory, crash reporting, SmartScreen) and report what each changes in what you can observe. Also test the **Fixed Version runtime** install mode if you can obtain it free: does it change what you observe, and what does it add to the size? State plainly what cannot be observed from the runner (traffic by system services, diagnostic data sent through Windows itself) so nobody mistakes "nothing observed" for "nothing sent".
  - macOS: `lsof` sampling plus `tcpdump`, as the Electron session did, and find out whether `wry` leaves the WKWebView fraudulent-website (Safe Browsing) check on. State confidence honestly.
  - Verdict: can a Tauri app credibly meet "nothing leaves the computer unless opted in" on each OS, and with what hardening?
- **Testing and driving (G3).** Make the real window drivable in CI on all three free hosted runners. Try the embedded-WebDriver route first (`@wdio/tauri-service`, which the docs say works on Windows, Linux and macOS without an external driver), then the community `tauri-playwright` plugin or `tauri-driver` where they apply. Run the same 16-test slice scenario that the Electron slice uses, as far as it can go, with screenshots. Report for each OS: which tool worked, what could not be done (native file dialogs, native menus, real OS key events, drag from the desktop), setup cost, flakiness over several runs, and that tool's maintenance state. Record the exact web view version on each OS in every run (WebView2 runtime version, the macOS version and WebKit build, WebKitGTK version) and **compare screenshots between two separate workflow runs on identical code and between runner image updates if you can**. Say whether the web view version can be pinned on each OS. Also check that the dialog takes keyboard focus.
- **Charts and grid (G4, G2).** The renderer runs in WebKit on macOS and Linux. Check ECharts and the virtualised grid render correctly and smoothly: canvas or SVG performance, scroll frame times, sort times, mixed-script text and fonts (compare with the Electron screenshots), and anything that looks different between engines.
- **Linux packaging and the sandbox.** Build the `.deb` and an AppImage with Tauri's bundler. On `ubuntu-24.04`, install the deb with `apt` as an ordinary user and launch it under Xvfb. Report: dependencies pulled in, whether the window renders (some graphics setups give a blank window; check what the CI runner does and whether `WEBKIT_DISABLE_DMABUF_RENDERER`-style workarounds are needed), and whether the web view's own process sandbox is on (inspect the web process command lines and seccomp state, and read what `wry` and WebKitGTK 4.1 do; one agent's reading of the `wry` source found no mention of a sandbox, which you should check). Compare with Electron's findings (the Chromium sandbox needs an AppArmor profile on Ubuntu 24.04, and an AppImage silently runs unsandboxed). Wayland and real GPUs cannot be tested on the runner: say so, and list what you could not measure.
- **Accessibility (F3).** Dump the platform accessibility trees (AT-SPI on Linux, UI Automation on Windows with the WebView2 tree, the macOS AX hierarchy) for the same elements and scenario as the Electron slice (reuse its scripts), especially the 10,000-row ARIA grid, a selected row, the legend rows and the dialog. Report where WebKitGTK and WKWebView differ from Chromium. NVDA through Guidepup on Windows is a stretch goal of about 30 minutes, as before.
- **macOS (F2).** Run the whole slice on `macos-latest` as the follow-up spec describes.
- **Dependencies and licences (G6).** List Rust crates (count direct and transitive, licences, any single-maintainer ones) with `cargo tree` or `cargo license`, plus the npm side. Check that no crate or plugin phones home.

## Use of subagents (approved by Jeremy for research only)

Jeremy has approved dispatching research agents for the pure research questions below, so they can run in parallel with your hands-on work. Subagents are read-only researchers: they read documentation, source code and issue trackers and report back. They must not edit files, push, open pull requests or issues, post comments, or run builds. Give each one narrow question, ask for URLs, versions, tags and line numbers, and ask it to separate what it read from what it inferred. **Treat everything they return as unverified.** Open the cited source yourself or reproduce the behaviour before relying on it, and in your results mark which findings came from an agent and how you checked them. Do not use subagents for building, measuring, or running CI.

Research questions suited to subagents: (a) what the `wry` source sets for WKWebView, WebKitGTK and WebView2 settings (Safe Browsing, hyperlink auditing, DNS prefetch, SmartScreen, additional browser arguments, data directory); (b) Microsoft's WebView2 data-privacy and Fixed Version documentation and any controls for the required diagnostic data; (c) the Tauri 2 bundler's WebView2 install modes and their sizes; (d) known issues in Tauri's tracker for large virtualised tables, ECharts, and WebKitGTK on Ubuntu 24.04; (e) the Tauri CEF runtime status.
