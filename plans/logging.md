## Goal

Make the main-process logger good enough to debug a failure on a household machine: log errors with their stack traces, never lose a line to a failing write, and keep a log file where a packaged app can be read afterwards. Diagnostic logs still carry no financial data and no personal data (AD-10, AD-18). When a scrubbed line is not enough, the person can hand over the raw details on purpose.

## Scope

- In, done: `apps/desktop/src/main/logger.ts` (error logging, a write that never throws), a stack scrubber, a small rotating file sink, the call sites in `main.ts` and `ipc.ts`, logging of uncaught errors, `FolioError` and the private-field mark, masked third-party messages and the developer-only unredacted switch.
- Approved, not started: saving diagnostic details (milestone 7, last): raw details kept in memory only and saved to a file the person chooses. Parked by choice, not blocked; see "Start here" under milestone 7.
- Out, for now: everything under "Later" below. Each item is recorded there so it is not forgotten; none is started.
- Out for good: uploading logs (nothing leaves the computer, H1.12).

## Approach

The proposal was to log errors as name plus stack frames only, with the message line removed and paths made relative to the app. That holds up, with these changes:

1. _Keep frames only, not "stack minus the first line"._ A stack's message can span several lines, and the message is where data hides (a parse error quoting a value). The scrubber keeps only lines that start with `at ` and rebuilds each frame, so nothing else survives.
2. _Paths: the app folder is kept, everything else is cut to the file name._ A path below the app folder (`<app>/main.cjs:120:5`) shows code layout and no one's data, so it keeps its folders. A path below the user's home folder, the temp folder or anywhere unknown can carry a user name or a folder name chosen by a person, so it keeps only the file name, line and column. This is stricter than "strip the roots" and cannot leak a folder that nobody thought to list. Backslashes, drive letters, UNC paths, `file://` URLs (percent-decoded before matching) and a different case of a drive letter are all understood. The roots are passed in, so the logger stays free of Electron and `node:os`.
3. _Name and code are checked, not trusted._ `name` is kept only if it looks like an identifier, else `Error`. A `code` such as `ENOENT` is kept when it looks like one: it is the most useful fact about a file-system failure and it carries no data. `message`, `path`, `syscall` and every other property are never read.
4. _Thrown values that are not errors_ (a string, an object, `undefined`) are logged as `NonError` plus their `typeof`, never their content.
5. _Limits._ A frame is cut at 200 characters, a stack at 20 frames, and a cause chain at 3 causes below the error. These are judgement, not measured. They are separate from the 120-character field limit, which stays as it is. A cut is marked (`truncated`), so it is not mistaken for the whole story.
6. _Where the line goes._ The log line gets an `error` object next to `fields`, so errors never share a key with caller fields.

Robustness gaps reviewed:

| Gap                                                                                                                                    | Decision                                                                                                                  |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| A throwing `write`, a throwing `now`, or a hostile getter on an error (`stack`, `cause`) could crash the app, or hang a request filter | Done: building and writing a line is wrapped; on failure the logger tries one fixed-text line and then gives up silently. |
| An error on `process.stderr` (for example EPIPE when the parent closed the pipe) is an unhandled `error` event and crashes the app     | Done: `main.ts` handles it.                                                                                               |
| Packaged builds have no console, so stderr is lost                                                                                     | Done: a log file (below).                                                                                                 |
| Level from `FOLIO_LOG_LEVEL`                                                                                                           | Already case-insensitive and trimmed; unchanged.                                                                          |
| Control characters, newlines, quotes in text                                                                                           | Already safe: `JSON.stringify` escapes them. Tested.                                                                      |
| Messages and fields may still be written with data by a caller                                                                         | Cannot be checked by the logger; the rule stays in the `LogFields` comment and in review.                                 |
| `AggregateError.errors`, `Error.stackTraceLimit` (V8 keeps 10 frames by default), async stack traces                                   | Not handled; ten frames is enough for now.                                                                                |

_Log file._ Needed now: the stack traces are of little use if a packaged app, which has no console, throws them away. The file is `folio.log` in `<userData>/logs`, written in packaged builds; unpackaged runs write the same file to `<userData>/logs-dev` instead (added with milestone 6), so a developer's logs never mix with an installed app's. Lines are appended synchronously, because the last line before a crash, `startup failed`, must reach the disk before `app.exit`. When the file would pass 1 MB it is renamed to `folio.log.1` and the older `.1` becomes `.2`; the old `.2` is deleted, so at most 3 MB are kept. Stderr still gets every line. The sink takes its file operations as an argument, so its unit tests need no real folder. Logs are never uploaded and are not part of a budget file or its backups.

## Milestones

### 1. Errors and a logger that never throws (done)

- Does: `logError` on the logger, the stack scrubber, the limits, the throw-proofing and the `main.ts` and `ipc.ts` call sites. `hardening.ts` needs no change: its one log call carries no error, and the logger's new guarantee is what protects the request filter.
- Acceptance criteria: unit tests with a fixed time source cover Windows and macOS path shapes, a message with data that must not appear, nested causes, non-error values and a throwing write.
- Verified by: lint, format check, type check, the architecture checks and the unit tests.

### 2. The log file (done)

- Does: the rotating file sink and its use in packaged builds.
- Acceptance criteria: unit tests over an in-memory file system cover appending, rotation, the backup cap and recovery after a failed operation; an integration test on a real temporary folder rotates a real file. That a packaged app writes `logs/folio.log` is not yet checked by the end-to-end smoke test.
- Verified by: the unit and integration runs.

### 3. Uncaught errors (done)

- Does: `installErrorHandlers` logs uncaught exceptions and unhandled rejections with `logError`, shows one fixed-text error box (later errors are logged only, so a loop cannot bury the window in dialogs), and keeps the app running. This replaces Electron's default dialog. Chosen for now and open to change (Jeremy, 2026-11-19): continuing after an unknown error can hide a broken state, so exit-after-logging is the alternative.
- Acceptance criteria: unit tests with a fake event source cover both events, non-error reasons, one box for several errors, and a box that throws.
- Verified by: lint, format check, type check, the architecture checks and the unit tests.

### 4. Positions, not values, and per-field privacy (done)

Why: the cheapest way to keep a useful message free of data is to never put the data in it. No crypto is needed for this.

- Does: a `FolioError` class whose message follows a message standard (fixed text plus ids, counts, dates, row and column numbers and file hashes, never a value) and is logged as written, also when it is a `cause`; code that catches a third-party error wraps it in a `FolioError` and keeps the original as the cause. Log fields get a per-field privacy mark, as in Apple's `os_log`: `privateField(value)` is written as `[private]` and its value never appears in a log line; milestone 7 keeps it in an in-memory buffer. An unmarked value behaves as before (strings are written and clipped, other values become `[omitted]`). Making unmarked strings private by default, as Apple does, would change every existing call site and is not done; the call sites are fixed text and reviewed. `FolioError` lives in `packages/core` so core code can raise it; the logger recognises it with `instanceof`, so a plain error that is merely named `FolioError` is still dropped.
- Acceptance criteria: unit tests that a `FolioError` message is written as is and a third-party cause is not; a private field never appears in a line; existing field behaviour is unchanged.
- Verified by: the unit run; AD-10 and this plan updated for the message rule. Whether the message standard also goes in `project-standards.md` is Jeremy's choice (not a stack rule).

### 5. Masked third-party messages (done)

- Does: vocabulary masking for every message that is not a `FolioError`'s. Quoted text is masked, a word is kept only if it is in a fixed list of error words, everything else becomes `<?>`, and a number is kept only after `position`, `line`, `column` or `index`. The masker fails closed: a word it does not know is hidden, not shown. Neighbouring masks merge into one, so even the number of hidden words is not shown; input is cut at 1000 characters before it is looked at. The result is written as `error.maskedMessage`, a different key from the `message` of a `FolioError`, so the two cannot be confused. The word list is `log-vocabulary.ts`; adding a word is a review item, and a test keeps names, brands and finance terms out of it. The word list was grown from 45 recorded Node and V8 messages (`RECORDED_MESSAGES` in the test, with the reviewed masked text for each, so any change to the masker or the list shows up as a diff to review); 80% of their words are kept. Variable, property and module names are never added, because they can come from data (`reading 'Acme'` when an object is keyed by payee). Known limitation: a message whose quoted text itself contains quotes (the newer `JSON.parse` message) is masked more heavily than needed, which is safe but loses detail; known-template extraction is in Later.
- Acceptance criteria: a test set of messages that hold data (amounts, account numbers, names, merchants, file names, emails, IBANs) in several shapes, none of whose values survive; `TypeError` and `ENOENT` style messages keep their structure.
- Verified by: the unit run.

### 6. Developer-only unredacted switch (done)

- Does: every log line gets an `id` (a short random session id, a hyphen and a counter, such as `k7q2m9-0042`), and `FOLIO_LOG_UNREDACTED=1` writes a second line with the same `id` next to a message that has an error or a `privateField`. The second line holds only what the normal line hides: the raw message, the raw stack, the words the masker hid and the private values, for the error and each cause, so the word list can be grown from real use; it is not a copy of the normal line, and `grep` for the id finds both. The code ignores the variable in packaged builds, so a household machine cannot be set to write personal data in the clear. Unpackaged runs also write a normal log file now, in `<userData>/logs-dev`: `folio.log` holds the normal lines, which stay safe to share, and `folio-unredacted.log` holds the second lines. Both rotate the same way (1 MB, two backups). The terminal shows both lines when the switch is on. The raw file stays on the developer's own machine, in the dev user-data folder, so it never goes into the repository. For packaged builds milestone 7 is the only way to see raw details; milestone 6 stays because a developer running an unpackaged build needs the plain text.
- Implementation: `parseUnredacted(env value, packaged)` is true only for an unpackaged run with the variable set to exactly `1`. `createLogDestinations` decides where lines go and again refuses an unredacted writer in a packaged build; `main.ts` wires it up and gives the logger a `sessionId` (`createSessionId`). The logger takes an optional `writeUnredacted` writer; when it is set, a call with an error or a private field writes the second line to it, marked `"unredacted":true` and holding `error.raw` for each cause (clipped at 2,000 and 8,000 characters), what was thrown when it was not an error, and the private values. A thrown string or object is shown as it is, because that is the point of the switch. The normal line is never changed.
- Acceptance criteria: tests that the switch works unpackaged and is ignored when packaged (no unredacted writer and no unredacted file), that the normal line is unchanged, that the second line has the same `id` and only the raw details, that no second line is written without an error or a private field, that ids count lines in order, skip those below the level and grow past four digits, that a failing unredacted writer cannot throw, that the destinations are routed as described, and that a custom file name rotates on its own.
- Verified by: the unit run.

### 7. Save diagnostic details (last)

Status: approved by Jeremy, 2026-11-24; implementation parked until asked for.

Start here:

- Branch `logging-m7-diagnostic-buffer` from the latest `main`; PR title `Logging milestone 7: ...`. Everything it builds on is merged: the error box (milestone 3), `privateField` (4), the raw-details path and line ids (6).
- New files, each with a test: `diagnostic-buffer.ts` (pure, no Electron, injected clock) and `diagnostic-save.ts` (builds the JSON, writes through injected file operations, takes the dialog as a function).
- Wiring: `logger.ts` feeds the buffer from the original error and fields, before anything is scrubbed; `error-handlers.ts` and the `startup failed` catch in `main.ts` (before `app.exit(1)`) get the button and the reference id.
- First check: whether a dialog with buttons can be shown before the app is ready. Handle the answer then; there is no fallback decision yet.
- Docs: AD-10 already describes this as the design; mark it built when it is, and add the new files to `key_files`.

Why: some failures cannot be debugged from a scrubbed line: the raw message, the raw stack, a value the code marked private. Instead of writing that to disk or encrypting it into the log, keep it in memory and let the person hand it over on purpose.

- Does:
  - An in-memory ring buffer of raw details only: the raw message, the raw stack and the `privateField` values of each logged error. The app never writes it to disk. It holds at most 200 entries or 1 MB (counted as the total length of the stored strings, an estimate), and the oldest entry is dropped first, where oldest means the one whose last occurrence is earliest.
  - Strings are truncated when they are stored, and an `Error` object is never stored: an object keeps live data reachable and can change after it was captured. The limits are 2,000 characters for a message, 8,000 for a stack and 500 for a private value (judgement, not measured).
  - A repeated stack collapses into one entry with a count and the first-seen and last-seen times. Two errors are the same when their names and raw stacks are the same; the entry keeps the message and private values of the latest one.
  - The line ids come from milestone 6: every log line already carries an `id` of the form `k7q2m9-0042`. A buffer entry stores the `id` of its first and last lines and of its most recent 20, and the saved file starts with the session id, so a person reading a collapsed entry can still find each line it stands for with one `grep`.
  - A "Save diagnostic details…" command in the main process. The person picks the location in a save dialog, and the dialog says the file contains budget details (amounts, names and descriptions) and should only go to someone they trust. The file is JSON: the app version, the platform, the session id and the entries. Nothing is written before the person confirms the location.
  - The uncaught-error box (milestone 3) and the startup-failure box offer "Save diagnostic details…" next to Close, and show the `id` of the line that was logged ("Reference: k7q2m9-0042", fixed text plus the id), so the person can quote it and a log line can be found. On a startup failure the box is shown before `app.exit(1)`. Whether a dialog with buttons can be shown before the app is ready is checked when this milestone reaches it, and handled then.
  - `crashReporter` stays off (AD-18). An operating-system crash dump of the app would contain the buffer, which the app cannot prevent; this is noted in AD-10.
- The menu entry for the command (the hamburger menu of H1.14 and the macOS menu bar of H1.16) is added with the menu plan; until then the command is reachable from the error boxes. This is in Later.
- Acceptance criteria: unit tests for the entry cap and the size cap, the eviction order, the collapse of repeated stacks (count, last-seen, latest message), the `id` format and that ids are unique within a session, the same `id` appearing in the log line, the buffer entry and the saved file, the error box text, truncation, and that no `Error` object is stored; a test with a recording file-operations fake that nothing reaches disk before the save, and that the save writes once, to the chosen path, after the confirmation; AD-10 and the Requirements amended (the consented save is the only exception to "no personal data in the clear").
- Verified by: the unit run, and the dialog and the error boxes by hand in a packaged build.

### Working conventions

- One branch and one pull request per milestone, in order. The branch is `logging-m{N}-{short-name}` (for example `logging-m4-positions-not-values`) and the pull request title starts `Logging milestone {N}:`. Branches start from the latest `main`. Milestones 1 to 3 shipped together before this convention (Jeremy, 2026-11-21).

## Requirements

- No financial data and no personal data in any log, including paths and error messages (AD-10, AD-18). The one exception is the consented save of milestone 7: raw details are kept in memory only, the app never writes them to disk, and they reach a file only when the person picks a location in the Save diagnostic details dialog, which says the file contains budget details.
- The crash reporter stays off (AD-18); an operating-system crash dump would contain the in-memory buffer.
- Logging never changes what the app does: it cannot throw, and it adds no network access.

## Decisions

- Milestone 7 is approved and its implementation is parked until asked for (Jeremy, 2026-11-24).
- Frames only, app-relative paths, everything else cut to the file name (Engineer, 2026-11-16; proposal changed from "strip the install, home and temp folders").
- A log file under the user-data folder in packaged builds, with 1 MB size rotation and two backups (Engineer, 2026-11-16; the owner asked for the decision to be made here).

- Raw details are kept in an in-memory ring buffer and saved to a file only when the person chooses; milestone 7 is "Save diagnostic details", and age sealing moved to Later (Jeremy, 2026-11-22). The sealing decisions (age format, per-install keys from an owner-held master secret kept in Bitwarden Secrets Manager and never given to CI, only Jeremy holding it, an environment variable first and a Settings toggle later) are recorded in the Later row.
- Uncaught exceptions and unhandled rejections: log, show one error box, keep running (Jeremy, 2026-11-19).
- Source maps for the main bundle wait for the packaging work (Jeremy, 2026-11-19).
- The message standard lives in AD-10 and this plan, not in `project-standards.md` (Jeremy, 2026-11-19).
- The end-to-end check of `logs/folio.log` stays in Later (Jeremy, 2026-11-19).
- Per-line ids are `session-counter` in one string, shown the same way in log lines, the unredacted file, the saved file and the error boxes, so a log entry and its raw details are easy to connect. They are built in milestone 6, because the unredacted file needs them; milestone 7 reuses them (Jeremy, 2026-11-22).
- The unredacted file does not repeat the normal line: it holds only the raw details, linked to the normal log by the line `id` (Jeremy, 2026-11-22).
- A repeated stack collapses into one entry that keeps the latest message: with the same stack, a meaningfully different message is unlikely, so the first message is not kept as well (Jeremy, 2026-11-22).
- `npm run dev` builds and starts the app unpackaged from the repository root, and a `.env` file there can set `FOLIO_LOG_LEVEL`, `FOLIO_LOG_UNREDACTED` and `FOLIO_AUTOMATION`, so engineers can drive a development run from the command line (AD-16). Packaged builds never read it, only those keys are used (it cannot set `GOOGLE_API_KEY`, `NODE_OPTIONS` and the like), and the real environment wins (Jeremy, 2026-11-22; `FOLIO_AUTOMATION` added after review, 2026-11-23).
- Unpackaged runs write a log file too, in `logs-dev`, and the unredacted details go to their own rotating file there (Jeremy, 2026-11-22; they asked for a written log in dev builds).
- Milestone 6 is kept: it is development-only and ignored in packaged builds, where milestone 7 is the only way to see raw details (Jeremy, 2026-11-22).
- Whether a dialog with buttons can be shown before the app is ready is dealt with when milestone 7 reaches it; there is no fallback decision until then (Jeremy, 2026-11-22).
- If a bug investigation stalls on hidden text, the list is not widened and no identifier mode is added: raise a `FolioError` with ids at that spot instead, and ask the person to save diagnostic details (milestone 7); consider the age sealing in Later only if neither is possible (Jeremy and Engineer, 2026-11-21, amended 2026-11-22).
- Order: positions-not-values and per-field privacy first, masking second, the developer switch third, saving diagnostic details last (Jeremy, 2026-11-19, amended 2026-11-22).
- Messages: own errors as written, third-party messages masked by vocabulary, known-template extraction left for later (Jeremy and Engineer, 2026-11-17).
